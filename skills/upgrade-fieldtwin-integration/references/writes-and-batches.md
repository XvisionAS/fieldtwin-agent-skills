# Migrating writes: batches, ownership and IDs

Use this reference for step 6 of the upgrade workflow. Every v2.0 mutation is a batch keyed by
resource type. Code that already used the v1.10 `/batch` routes will find the envelope familiar;
code that used the per-resource routes changes the most. All identifiers are fictional.

## Batch bodies and responses

| Verb | Body | Response |
| --- | --- | --- |
| POST | `{ "TYPE": { "items": [ {...} ], "globals": {...}, "totalNumberOfItems": 2 } }` | `200` with `{ "TYPE": ["NEW_ID", "..."] }` |
| PATCH | `{ "TYPE": { "ID": {...}, "globals": {...} } }` | `200` with `{}` |
| DELETE | `{ "TYPE": ["ID", "..."] }` | `200` with an empty body |

`globals` is applied to every item; an item's own fields win.

## Rules that change how the code is written

- **Responses carry IDs only.** v1.10 returned `{ "id": "..." }` or the created object from a
  POST and the updated object from a PATCH. v2.0 returns IDs from POST and nothing useful from
  PATCH or DELETE. Code that used the response body as the new state has to read it back with
  `?resourceTypes=TYPE&resourceIds=ID`.
- **A batch is all or nothing.** One unknown ID rejects the whole request with `422` and a message
  such as `Invalid wellTypes:ID for account.`, `... for project.` or `... for subProject layout`;
  on DELETE the message is `Invalid wellTypes "ID" for project "PROJECT_ID"`.
- **One batch stays inside one stream.** A failure in a second stream cannot undo the first, so
  order cross-stream work deliberately and make each step safe to resume.
- **Unknown top-level types and unknown fields are dropped silently**, as they were in v1.10. A
  body that only contains them answers `200` and changes nothing. A misspelt type key or a field
  that kept its v1.10 name therefore looks like success. Verify by reading back.
- **An API token must name `updatedBy`** on a project or sub-project PATCH unless the PATCH only
  changes `vendorAttributes`; without it the answer is `422` `Missing "updatedBy" field`. A user
  JWT does not need it. `updatedBy` is the e-mail address of the user making the change, and it
  replaces the v1.10 body field `userEmail`, so a v1.10 caller that sent `userEmail` already has
  the value.
- **Order still matters inside a batch.** Types are processed in the order of the keys in the
  body: assets before the connections that use their sockets, connections before connection
  segments, wells before wellbores before wellbore segments, types before the resources that use
  them, metadata definitions before groups and links, `workflowColumns` before
  `workflowTemplates`.
- **Create and delete on the owning stream.** Projects belong to the accounts stream and
  sub-projects to the projects stream. Sending a stream's own root to its own `DELETE` is refused
  with `403` and `Cannot delete projects from its own stream` (or `Cannot delete subProjects from
  its own stream`).
- **PATCH and DELETE bodies must not be parsed blindly.** Check the status, then the content
  type, before calling a JSON parser.

## IDs

- A client may choose the `id` of most account- and project-level resources (types, tags,
  metadata definitions, templates, connection definitions and so on).
- A client cannot choose it for projects, sub-projects, users, documents, tree view folders or
  link records, and never on the subProjects stream, where a client ID is dropped.
- A duplicate client ID answers `409` `wellTypes already defined with id ID`.
- There are no temporary IDs. A resource can refer to another one from the same request only when
  that one has a client ID and comes earlier in the body.
- On the subProjects stream every ID is generated by the server, so a dependent resource takes a
  second request.
- A sub-project created through `POST /projects/ID` comes back as a qualified `SUBPROJECT:STREAM`
  ID.

## Example: create a staged asset

v1.10 put the transform under `initialState`. v2.0 takes it flat, and `x` and `y` are required.

```http
POST /API/v1.10/project-01/subProject/subproject-01:stream-01/stagedAsset
```

```json
{
  "asset": "asset-definition-01",
  "name": "Manifold M-01",
  "initialState": { "x": -37.3, "y": 0.3, "z": -1200, "rotation": 49, "scale": 2.1 }
}
```

The v1.10 answer was `{ "id": "asset-01" }`.

```http
POST /API/v2.0/subProjects/subproject-01:stream-01
```

```json
{
  "stagedAssets": {
    "items": [
      {
        "asset": "asset-definition-01",
        "name": "Manifold M-01",
        "x": -37.3,
        "y": 0.3,
        "z": -1200,
        "rotation": 49,
        "scale": 2.1
      }
    ]
  }
}
```

The v2.0 answer is `{ "stagedAssets": ["asset-01"] }`. Reading it back shows the flat fields, the
ID of its asset definition and the qualified sub-project it belongs to:

```json
{
  "stagedAssets": {
    "asset-01": {
      "id": "asset-01",
      "asset": "asset-definition-01",
      "x": -37.3,
      "y": 0.3,
      "z": -1200,
      "rotation": 49,
      "scale": 2.1,
      "isLocked": false,
      "connectionsAsFrom": [],
      "subProject": "subproject-01:stream-01",
      "lastModified": "2026-11-06T09:12:44.102Z"
    }
  }
}
```

`initialState` is not a v2.0 field. A body that carries the transform only there is missing the
required flat `x` and `y`, so it is rejected. A body that sends both keeps the flat values and
ignores `initialState` without an error, which is why a half-migrated body can look correct.

## Example: update several staged assets

v1.10 had `PATCH .../stagedAsset/ID` for one resource, and `PATCH .../stagedAssets` with the IDs
at the top level of the body. v2.0 nests the IDs under the type:

```http
PATCH /API/v2.0/subProjects/subproject-01:stream-01
```

```json
{
  "stagedAssets": {
    "globals": { "showCustomResults": true },
    "asset-01": { "costObject": { "value": 26 } },
    "asset-02": { "name": "Pump P-102" }
  }
}
```

The answer is `200` with `{}`; v1.10 returned the updated resource.

Patching a stream's own root uses the same shape, keyed by the root's ID. On
`PATCH /subProjects/ID` only the `subProjects` entry that matches that sub-project's own ID is
applied; to patch several sub-projects in one request, use the projects stream.

## Example: delete

v1.10 deleted one resource per call. v2.0 deletes ID arrays per type, across types, in one
request:

```http
DELETE /API/v2.0/projects/project-01
```

```json
{
  "wellTypes": ["well-type-01"],
  "layerTypes": ["layer-type-01"],
  "virtualAssets": ["virtual-asset-01"]
}
```

The answer is `200` with an empty body. To delete a sub-project, send
`{ "subProjects": ["subproject-01:stream-01"] }` to the projects stream, not to the subProjects
stream.

## Example: metadata definition and link

The lower-case v1.10 paths become resource types on the accounts (or projects) stream, and the
definition's `type` is now `kind`:

```http
POST /API/v1.10/metadatadefinition
```

```json
{ "name": "Pressure rating", "vendorId": "EXAMPLE#12", "type": "connection", "cost": 0, "public": true }
```

```http
POST /API/v2.0/accounts/account-01
```

```json
{
  "metaData": {
    "items": [
      {
        "id": "example-pressure-rating",
        "name": "Pressure rating",
        "vendorId": "EXAMPLE#12",
        "kind": "connection",
        "cost": 0
      }
    ]
  },
  "metaDatumLinks": {
    "items": [
      { "metaDatum": "example-pressure-rating", "relateToType": "layers", "relateToId": "layer-type-01" }
    ]
  }
}
```

The v1.10 `public` field is left out on purpose: the FieldTwin 9.0 write schema for `metaData`
does not list it, so sending it would be a silent drop. Renames are not the only change between
the two bodies; check every field of a migrated body against the tenant's OpenAPI document.

Because `metaData` comes before `metaDatumLinks` in the body and the definition has a client ID,
the link can refer to it in the same request. Link `relateToType` values are the plural collection
names (`layers`, `assets`, `wellBores`, `annotations`), link IDs are generated by the server,
`order` cannot be set, and a second link to the same target answers `409`.

## Dependent resources on the subProjects stream

v1.10 nested the parent in the path. v2.0 moves it into the body, and because sub-project IDs are
server-generated, a new parent and its new child cannot share one request.

```http
POST /API/v1.10/project-01/subProject/subproject-01:stream-01/well/well-01/wellBore
```

becomes, for a well that already exists:

```http
POST /API/v2.0/subProjects/subproject-01:stream-01
```

```json
{ "wellBores": { "items": [{ "well": "well-01", "name": "Bore A" }] } }
```

For a new well and a new wellbore, send two requests: create the well, read its ID from
`{ "wells": ["well-01"] }`, then create the wellbore with that `well`. The same applies to a
connection between two new staged assets, a connection segment on a new connection
(`connection` required) and a wellbore segment on a new wellbore (`wellBore` required).

If the second request fails, the first has already committed. Either delete what the first one
created or report the partial state; do not leave it unmentioned.

## Upload documents

File uploads keep a dedicated multipart endpoint per scope: `PUT /accounts/ID/documents`,
`PUT /subProjects/ID/documents` and `PUT /workflowTasks/ID/documents`, each limited to 50 MB per
request. Let the HTTP client set the multipart boundary.

- A document record that points at an existing URL is the `documents` type on the same stream.
- Deleting a document deletes its revisions; a single revision is deleted with
  `{ "documentRevisions": ["ID"] }` on the stream that owns the document.
- A workflow task template's document is added on the accounts stream, through the upload
  endpoint or the `documents` type, with `relateToType: 'workflowTaskTemplates'` and `relateToId`
  set to the template ID.

## Users and roles

- `POST /users`, `PATCH /users` and `DELETE /users` manage organisation-level user records
  (licence, IT admin, folder admin). They accept a JWT of an IT admin or super admin only; an API
  token gets `403`.
- Account membership is the `users` type on the accounts stream. `POST /accounts/ID` with `users`
  needs `userRoleId` for every user (`Administrator`, `Editor`, `Viewer` or the ID of a custom
  role) and sends the invitation. `DELETE` of `users` on the accounts stream removes the user from
  the account and its projects; it does not delete the user.
- The v1.10 `delete-from-instance` header is gone. Its replacement, `DELETE /users` with the body
  `{ "users": ["ID"] }`, removes the user from every account and project unconditionally, where
  v1.10 only did so when no other account remained. This widens the effect of an existing call, so present the difference to the
  user and let them choose between account removal and organisation-wide removal.
- `GET /users/whoami` replaces guessing: it returns `me.credential` (`jwt`, `apiToken` or
  `delegated`, the last being an embedded-integration token), the account the credential belongs
  to as `me.account` and, for a JWT, the role and rights in each account and project under
  `me.accounts`.

## A write helper that verifies

Because unknown keys are dropped and responses carry only IDs, a migrated write is not finished
until the result has been read back. One helper keeps that from being forgotten at each call site:

```javascript
async function createAndReadBack(apiFetch, streamPath, resourceType, items) {
  const response = await apiFetch(streamPath, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ [resourceType]: { items } }),
  })
  if (!response.ok) {
    throw new Error(`FieldTwin API returned ${response.status}`)
  }

  const created = (await response.json())[resourceType] || []
  if (created.length !== items.length) {
    // The type key or its fields were not accepted; nothing may have been written.
    throw new Error(`Expected ${items.length} ${resourceType}, the API created ${created.length}`)
  }

  const query = new URLSearchParams({
    resourceTypes: resourceType,
    resourceIds: created.join(','),
  })
  const readBack = await apiFetch(`${streamPath}?${query}`)
  if (!readBack.ok) {
    throw new Error(`FieldTwin API returned ${readBack.status}`)
  }
  return (await readBack.json())[resourceType] || {}
}
```

Do not retry a POST automatically after a timeout: the write may have committed. Look the result
up by a stable external identifier before sending it again.
